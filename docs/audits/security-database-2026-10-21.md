## Исправления

Первопричина: обработчик принимал только sender.label == core, но у core нет models.py. Django не отправляет post_migrate приложениям без модуля моделей. Это воспроизведено реальным диспетчером установленного Django; правило также описано в [документации Django](https://docs.djangoproject.com/en/5.2/ref/signals/#post-migrate).

Минимальная правка: существующий обработчик запускается по сигналу accounts — приложение всегда установлено, содержит модель ученика и получает post_migrate. SQL защиты и архитектура сохранены. Добавлены быстрый тест реального диспетчера без БД и проверка состояния всех public-таблиц в существующем PostgreSQL-классе тестов. Ни один существующий тест не ослаблен.

До исправления оба новых теста упали. После исправления тест диспетчера прошёл за 0.002 с; реальная PostgreSQL-проверка прошла в составе 23 проверок. На новой базе RLS включён на 35/35 таблицах, anon/authenticated видят 0 аккаунтов и меняют 0 строк, отдельная роль приложения читает оба аккаунта. Повторный migrate на исходной тестовой базе с No migrations to apply тоже включил RLS на 35/35 таблицах и сохранил оба аккаунта. Новых файлов миграций нет, структура полей не менялась, данные не удалялись.

Одна находка — один коммит в audit/security-database-20261021. В него входят правка, два регрессионных теста и этот отчёт с доказательствами. PR создаётся черновиком; слияние и применение к рабочему сайту в эту работу не входят.

## Риски

Исправление находится в отдельной ветке и само по себе не защищает уже работающий сайт. На Supabase с широкими grants обнаруженный дефект позволяет читать и менять аккаунты в обход Django. Был ли такой доступ возможен на действующем проекте и происходил ли он — неизвестно.

При применении существующей защиты RLS роль сайта должна иметь предназначенную ей политику: migrate выполняется владельцем таблиц с корректным APP_DB_ROLE, как требует docs/operations/database-role.md. Иначе отдельная роль сайта может потерять доступ. Проверено на искусственной ee_audit_app; её соответствие рабочей роли не установлено. Существующие разрешающие политики патч не удаляет; они требуют отдельной проверки на действующем проекте. Откат только Python-правки не выключает уже включённый RLS.

Предупреждения W005/W021 не исправлялись автоматически: HSTS для поддоменов и preload зависят от реального домена. Локальные предупреждения режима разработки не объявлялись дефектами production.
